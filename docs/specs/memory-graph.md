# Memory graph, search and memory setup

Status: building (integration branch `feat/memory-graph`). This spec is the contract for the pieces built in parallel and the standing reference for every later change to Quorum's memory. Audit and research behind it: the memory audit (2026-11-19), Graphify (Apache 2.0), Zep and Graphiti (temporal knowledge graphs), and the context rot literature (Chroma 2025, Liu et al. 2024).

## Goal

When a person creates a second brain in Quorum or connects an existing one, Quorum ends with a complete, working memory: a graph of notes, people, projects, meetings and decisions with typed, sourced and dated connections; hybrid search across the whole vault; a setup report that lists every gap as a Needs review item Quorum can fix on Approve; and MCP tools that let AI tools query all of it. The memory stays correct as it grows: facts that change are superseded, retrieval stays small and relevant, and the maintainer layer keeps it clean.

## Principles

1. **Local first.** Everything in this spec runs on the Mac with no model calls, except the optional model pass (wave 2), which uses the person's own model source. No note text leaves the Mac in the Local edition.
2. **The vault is the source of truth.** The graph and the search index are derived data in Quorum's app data, rebuilt from the vault at any time. Quorum writes to notes only through Review items the person approves (or the auto-apply setting), with versions and Undo, like every other memory fix.
3. **Graph first.** Retrieval starts from the graph; keyword and vector similarity are signals in one ranker. The eval decides the weights.
4. **Every connection says where it came from and when.** Provenance and validity time on every edge.
5. **Small, high-signal context.** Every retrieval tool takes a token budget, returns the best items first, and says what it left out.

## Storage

One SQLite database per vault, in app data: `DATA_DIR/memory/<vault-hash>/memory.db`, opened with Electron's built-in `node:sqlite` (`DatabaseSync`, Node 24.22, FTS5 available). WAL mode. A schema version in `meta`; a version change rebuilds from the vault. The database lives in the main process; the memory engine utility process opens its own read-only connection where it needs one.

### Tables (owned by `app/graph/store.js`)

- `meta(key text primary key, value text)`
- `files(rel text primary key, hash text, mtime real, size int, indexed_at real)`: one row per note; `hash` is sha256 of the text, so unchanged files are skipped.
- `nodes(id text primary key, kind text, name text, rel text null, props text json, created_at real, updated_at real)`. Kinds: `note`, `person`, `project`, `company`, `meeting`, `decision`, `topic`, `tag`, `folder`. A node backed by a note has `rel`; a person mentioned with no note has none (a gap). Ids are stable: `note:<rel>`, `person:<slug>`, `tag:<name>`, and so on. When two notes that could be one kind of entity share a file name slug, they are one entity if one's folder holds the other: a hub and the note beside its folder (`projects/Orca.md` and `projects/Orca/Orca.md`), or a hub and a note inside its folder. That entity keeps the slug id; its typed note backs it, else the deeper note, and the other notes are notes `about` it. Notes in unrelated folders (`projects/alpha/Orca.md`, `projects/beta/Orca.md`) are separate entities, each under the path of its backing note (`project:projects/alpha/Orca`), and `find` returns both as candidates. The rule is `extract.js` `entityIds`; the graph applies it to the whole vault at each pass and reads a note again, with its linkers, when its id or backing changes.
- `aliases(node text, alias text, primary key(node, alias))`: normalized lowercase names for lookup and for merge detection.
- `edges(id integer primary key, src text, dst text, kind text, provenance text, source_rel text, source_line int null, confidence real, valid_from real null, valid_to real null, superseded_by integer null, recorded_at real, props text json null)`. `props` holds what a single-valued fact competes on: a `works_on` role, a decision key.
  - Kinds: `links_to`, `embeds`, `mentions`, `attended`, `works_on`, `member_of`, `decided_in`, `decision_about`, `about`, `tagged`, `in_folder`, `contradicts`, `supersedes`.
  - Provenance: `explicit` (a wikilink, embed or frontmatter field written in the note), `rule` (a folder or naming convention, a meeting template, the keeper's name match), `model` (the model pass read it from prose; it carries the source line and the model's confidence), `person` (approved in Review).
  - Validity (bi-temporal): `valid_from` and `valid_to` are when the fact held in the world (from the note's date, a meeting date, frontmatter dates); `recorded_at` is when Quorum learned it. A newer fact that replaces an older one sets the older edge's `valid_to` and `superseded_by` and keeps it for history.
- `edges_by_src`, `edges_by_dst`, `edges_by_kind` indexes.
- `communities(node text primary key, community text, rank real)`: each clustered node's community and its rank in it (weight inside the community over the strongest member's, so the hub is 1).
- `community_info(id text primary key, name text, named_by text, size int, rank real, hub text, props text json, updated_at real)`: one row per community, biggest first (`rank` 1). `named_by` is `rule` or `model`; `props` holds the shared `tags` and `folder`, `nameSig` (the strongest members, so a model name stays while they hold), `sourceSig` (the members' notes and their hashes) and a model summary `draft` with the `sig` it was written from. Added in wave 2 with `create table if not exists`, so the schema version did not change. A node that goes leaves `communities` at once, and a community it was the hub of goes until detection runs again.
- `model_files(rel text primary key, hash text, read_at real, tokens int)`: the notes the model pass read, by the hash of the text it read, so a run reads only notes that changed or that it has not reached. A schema rebuild drops it with the edges, so the pass reads those notes again.
- `model_proposals(id, key text unique, rel, line, kind, src, dst, confidence, props json, status, edges json, recorded_at, decided_at)`: readings the model pass made under its bar, or that name something the graph has no node for. `status` is `pending`, `approved` (`edges` holds the edges and decision node the approval added) or `declined`. They are never edges, so no query, search boost or tool reads one as fact. The table outlives a schema rebuild, so an approval or a decline keeps its answer: a declined reading of a note is never proposed again, and an approved one is added again as the person's when the note is read again.

### Tables (owned by `app/search/`)

- `chunks(id integer primary key, rel text, heading text, start_line int, end_line int, text text, hash text, tokens int)`
- `chunks_fts` (FTS5 over heading and text, porter tokenizer, external content `chunks`)
- `vectors(chunk integer primary key, model text, dim int, vec blob)`: float32, normalized.
- `search_files(rel text primary key, hash text, title text, kind text, date real, mtime real)`: one row per indexed note, so an unchanged note is skipped and the filters and the recency factor read the note's kind and date without the graph. Search's schema version is the `meta` key `search_schema`.

## Modules and their APIs

### `app/graph/` (agent: graph-core)

- `store.js`: `openStore({ dir, vault, log })` returns the store with `tx(fn)`, `upsertFile`, `fileHash(rel)`, `removeFile(rel)` (drops its nodes' derived edges), `upsertNode`, `addEdge`, `supersede(edgeId, byEdgeId, at)`, `node(id)`, `find(name, { kind, prefix = true })` (exact, alias, then prefix of 3 or more characters; returns every match so callers can refuse ambiguity; prefix matches carry `prefix: true` and are only candidates), `edgesOf(id, { dir, kinds, current = true })`, `stats()`, `close()`.
- `extract.js`: pure. `extractNote({ rel, text, note, resolve, conventions })` returns `{ nodes, edges }` from one note, with no model: links and embeds (through vindex's resolver), frontmatter (`type`, `people`, `attendees`, `project`, `projects`, `company`, `tags`, `date`, `status`, `aliases`), inline tags, folder conventions (configurable; defaults detect `people/`, `projects/`, `companies/`, `meetings/` or `08-meetings/`, `decisions/`), meeting notes (attendees and date), decision lines (`Decision:`, `Decided:`, `- [x] Decision`, a `## Decisions` section) and the keeper's link lines.
  - A note in a meetings or decisions folder is a meeting or a decision. A note in a people, projects or companies folder is that entity only when its frontmatter `type` says so, when it is the folder's hub note (named like the folder it sits in, `projects/Atlas/Atlas.md`), or when another note links it as one: an `attended`, `works_on` or `member_of` edge on its entity node, or an `about` edge from a meeting or a person (a meeting's attendees, a project field). Every other note in those folders (specs, PRDs, research, lists) is a note, and a link to it is no mention of an entity. `extractNote` takes `linkedAs(rel)` and `kindOf(rel)` for this; `index.js` answers them from the store and reads a folder note again, with the notes that link it, when its answer changes.
- `temporal.js`: pure. Given the current edges for a subject and a new edge of a single-valued kind (`works_on` with role, `member_of`, a decision on the same subject), decides whether it supersedes an older one; returns the supersede pairs. Two decisions compete only when they share a subject and a key, the short label before a colon ("Database: Postgres"); decisions without a key never replace each other. Dated facts compete by `valid_from`; undated facts replace each other only when the same note was edited.
- `query.js`: `graphQuery({ q, seeds, budget, depth = 2, kinds, current = true })` (seed nodes from `find` and from search hits, breadth-first expansion, scored by edge kind and provenance, trimmed to `budget` tokens, returns `{ nodes, edges, truncated: { shown, total, budgetNeeded } }`); `graphPath(a, b, { undirected })`; `explain(id, { budget })` (the node, its source, aliases, community, incoming and outgoing edges with provenance, superseded history); `entity(name)` (a person, project or company with meetings, decisions, notes and people around it); `decisions({ about, since, current = true })`. A name that matches several nodes, or only the start of a name, returns `{ ambiguous: [candidates] }` and never guesses. `explain`, `entity` and `decisions` read out only what their budget shows; their `truncated` counts the rest.
- `index.js`: `createMemoryGraph({ dataDir, vault, vindex, log })` wires the store to vindex: a full build on connect (batched, yields to the event loop, reports progress), then incremental updates from the watcher by content hash, including moves (vindex's `onMoves`). Emits `progress` and `ready`.

### `app/search/` (agent: search)

- `chunk.js`: pure. Splits a note into heading-scoped chunks of at most 400 tokens with a short overlap, keeping the note title and heading path on each chunk.
- `embed.js`: an embedder interface `{ id, dim, embed(texts) }`. The default is the bundled bge-small-en-v1.5 int8 in the memory engine's utility process (raise its max tokens to 512 for chunks). The interface leaves room for another local model or a hosted provider later; nothing hosted ships in this wave.
- `index.js`: incremental chunking, FTS and vector updates keyed by chunk hash; a background embed queue that never blocks the window and pauses while recording.
- `hybrid.js`: `search({ q, budget, k = 20, folders, kinds, since })` (`kinds` are graph node kinds, from the same frontmatter types and folder conventions as `extract.js`): BM25 from FTS5, cosine over vectors (brute force is fine up to a few hundred thousand chunks), graph boost for chunks in notes near the top hits' nodes, recency and supersession factors, merged with reciprocal rank fusion. Returns chunks with `rel`, heading, line range, score parts and a `truncated` summary.
- `eval/`: a local eval harness: a question set with expected notes (built from real questions over a vault, kept out of the repo when it names private content), recall@5, recall@10 and MRR for keyword only, vector only, graph only and hybrid. Used to set the weights and to judge any future model change.

### MCP and CLI tools (agent: mcp)

In `app/cli/` through the app bridge (`appTools.mjs`), each with a `budget` argument (default 1,500 tokens) and a truncation line that says how much was left out and the budget that would return everything:

- `search`: hybrid search over the whole vault and meetings.
- `graph_query`, `graph_path`, `explain`, `entity`, `decisions`.
- `communities`, `hubs` (wave 2): topics in the vault and the most connected nodes; see Communities below.
- `memory_status`: setup progress, index counts, open gaps.

The tools are defined in `app/cli/memoryTools.mjs` and run in the app through one control socket command, `memory_tool`, which calls the IPC handler each tool names (`memory-search`, `memory-search-status`, `memory-graph-query`, `-path`, `-explain`, `-entity`, `-decisions`, `-communities`, `-hubs`, `-status`), answers "not ready" while a handler is missing (search also answers not ready until the vault index finishes its first read), and withholds opted-out notes and lines. The window's IPC reads go through the same filter. An item is withheld when its id, name, path, aliases or edge end names (`srcName`, `dstName`) name an opted-out customer, slug forms included (`company:acme-corp`). A change to the opt-out list reads the vault index again, so the names also leave the graph and search tables. `app/cli/budget.mjs` (pure) turns each answer into lines: one per node, edge, passage or decision with source path and line (counted from 1 for agents and editors; the index and graph store lines from 0), provenance and dates, strongest first, then a summary line. A name that matches several nodes returns the candidates. All are read only, so read only mode allows them; the in-app chat's connectors-only server does not list them. `quorum memory search|graph|path|explain|entity|decisions|communities|hubs|status` runs them from Terminal.

Update `about.mjs`, the instructions (under 2,048 characters), the README "For AI agents" section and the tool tests. Instructions tell agents to start with `entity`, `decisions` or `search` before reading files.

### Memory setup and the maintainer layer (agent: setup)

- **Scan** (`app/memorySetup.js`): runs on create and on connect, and again from Settings, Memory. It reports notes indexed, links resolved, entities found, embeddings built, and the gaps below, with progress until done.
- **Gaps become Needs review items**, each with a Quorum fix on Approve, through the existing review rules, quality gate, fix runs, versions and Undo:
  - a name mentioned in several notes with no person or project note (create the note from a template, linked from where it is mentioned);
  - one person or project under two names (add an alias, or merge on Approve);
  - meeting notes with attendees in text and no links (link them);
  - notes the graph reads as people or projects with no type in frontmatter (add it; one item per folder that lists its notes, and Approve sets the type on the notes the person keeps ticked);
  - notes the conventions cannot place (suggest a folder);
  - broken links and orphans (existing rules).
- **Setup screen** in onboarding for an existing vault and in Settings, Memory: what was found, what Quorum will fix, the keeper offered for connected vaults, the model pass offered with an estimate (below), and a done state. The keeper offer is shown selected, with one line on what it writes, and writes nothing on its own: the keeper turns on when the person finishes onboarding with it selected, or toggles it. The choice (on or off) is kept per vault (`memory-setup.json`), and a keeper turned off in Settings before setup counts as a choice, so a later render or step never overrides it. The scan's steps each check that the vault is still the one connected and stop with a reason when a build times out, so a partial scan saves no report.
- **Maintainer alignment.** The keeper writes typed edges through the graph store when it files a meeting (attended, mentions, decided_in) as well as its link lines. Review rules read the graph (orphans from edges, duplicates from aliases). The contradiction checker reads current edges and records `contradicts`; a resolved contradiction supersedes the losing fact. Learned facts come from current edges first.
- **As built (wave 1).** The gaps are the rules `note.missing-entity`, `note.entity-alias`, `note.meeting-links`, `note.entity-type`, `note.unplaced`, `note.summary-stale` and `note.instructions` (`rules/index.js` SETUP_RULES), plus duplicates (merge on Approve), oversized (split on Approve), orphans and broken links. Their fixes add the ops `create`, `mention`, `alias`, `merge` and `split` to the fix run (`memorySetup.js` runSetupOp). The rules read the graph in the memory engine through a read-only store (`openStore({ readOnly: true })`) once main reports the graph ready, and fall back to the notes when it is not. Approved mentions record `person` edges; Undo removes them. Instruction files at the Agent OS root, outside the vault folder, are measured and listed in the report; Quorum's fixes write only inside the vault, so those files get no Review item. An instruction file over its budget gets an item with no fix: Claude Code and Codex do not follow wikilinks, so a section split into a linked note would stop loading, and the oversized rule leaves instruction files alone for the same reason. Its dead links are the broken link check's items. Duplicates read graph aliases, and two notes under one name merge only when one of them sets that name as an alias and their bodies share at least 30% of their words; dated notes, meetings and decisions never merge by name, and neither do notes on two sides of a confidential mark. A merge refuses to run when a note the index leaves out links to the note it would trash. Duplicates from vectors were measured on a real vault and do not ship (see Real-vault eval).

### Model pass (wave 2: `app/memoryModelPass.js`, `app/rules/modelEdges.js`)

Reads the prose of notes for what links and frontmatter do not show: the people, projects and companies a note names (`mentions`), `works_on` with a role, `member_of`, `attended` for a meeting note, and decisions (`decided_in`, `decision_about` with a key). It runs on the person's own model source (the final notes provider, `runModel` with role `notes`, on `MEMORY_MODELS.relations` in `memoryModels.js`), and on nothing else.

- **Off by default, per vault, with consent tied to the source.** Memory setup and Settings, Memory offer it in the setup card; the choice, the token cap and the model source it was turned on for (provider and model, `models.js` modelLabel) are kept per vault in `memory-setup.json`. The switch stays off until the estimate and a provider are on screen, and the cap is chosen before the first run. The card says that turning it on starts reading now and keeps reading new and changed notes. In onboarding the switch only selects, and the pass starts when the person finishes setup, as the keeper does. When the notes provider or its model changes, the pass waits (`source-changed`) until the person sees the new estimate and confirms. Turning it on, Run now, Confirm and Cancel come from the window only; the control socket and the MCP tools cannot start it. Turning it off stops a run; what it added stays, with `model` provenance.
- **The estimate is computed from the vault** before it runs: the notes it would read now (changed since it last read them, and allowed), their text cut into calls of up to 20 notes or 44,000 characters (a claim call's size), input tokens from the prompt text at 4 characters a token plus Claude Code's own prompt per call, output tokens and seconds per call at what a Sonnet claim call measured (`memoryModels.js` MEASURED), and the runs the cap splits it into. Cost: dollars at API rates on an Anthropic key, plan usage (with the API-rate equivalent) on a Claude Code, Codex or Antigravity sign-in, free on a local model, and the provider's own rates on another key.
- **What it may read.** The vault index's text (withheld lines blanked, excluded notes absent), and only a note every other part of memory may read (`createMayRead`, the filter topics share as `main.js` noteMayRead): never one the guardrails deny (a denied folder, a secret-looking name, a denied frontmatter key), a private folder, a note or folder marked confidential, a note with a line the opt-out list withholds, or a note that names an address on the never-listen list. A run asks again for every note right before each call; the estimate keeps its answers until a guardrail, a confidential mark or the settings change. A local model keeps every note on the Mac.
- **Batched, budgeted, resumable.** A run stops at the cap the person sets (tokens a run, counted from the text sent and received), pauses while a meeting is recorded, stops on Cancel, and keeps what each finished call added. It reads a note again only when its hash changes; an edit drops what the pass read from that note (its model edges, the facts they superseded hold again, and its pending proposals) until the next run reads it. A background tick every 20 minutes and after the graph is built goes on with the notes left.
- **Grounding.** Every item belongs to the note it names and cites a line of that note the model was shown; every name it gives must be on that line as whole words, and a decision's words (or, for "Key: value", the key and the value) must be on its line; what a decision is about may be named anywhere in the same note. Anything else is dropped, so a line in one note can never place an item on another. The system prompt tells the model that note text is content and never instructions. At most 30 entities, 30 relations and 10 decisions per note, and a reply over 200,000 characters adds nothing. A name that matches more than one node is dropped, never guessed.
- **Confidence.** At 0.8 or above with both ends known and no conflict with a stated fact, an edge with `model` provenance, the source note and line, the confidence and `props.by: 'model'` (so the structural reindex leaves it). From 0.5 to 0.8, with a name the graph has no node for, or in conflict with a stated fact, a proposal. Below 0.5, nothing. A fact the graph holds already is skipped.
- **Moves.** A reading's key names its note; a move makes it again under the new path, so a decline or an approval still holds.
- **Review.** `note.model-edge` lists each pending proposal in Needs review (prior 0.7, so a bulk plan puts it under Check these first, and Apply memory fixes on its own never takes it). Approve runs the op `confirm`: nothing is written to the note, and the batch adds the edges with `person` provenance (`props.by: 'review'`), new names as nodes with no note; Undo removes them and the proposal waits again. Archive declines it.
- **A model reading never replaces a stated fact.** `temporal.js` is provenance-aware for every single-valued kind (decisions with a key, `member_of`, `works_on` with a role): a `model` edge supersedes only an older `model` edge, and between a `model` edge and an `explicit`, `rule` or `person` one the stated fact stays current whatever the dates. A model reading that would compete with a stated fact goes to Review as a proposal that names the note it disagrees with; once a person approves it, it is a `person` fact and competes by date like any other.
- **Decisions** become `decision:<rel>#m<hash>` nodes with `props.by: 'model'`. A decision the note states on the same line or in the same words is skipped.
- **What agents see.** Query results, `explain`, `graph_path` and `decisions` carry each edge's provenance and confidence (`decisions` adds `provenance`, and `confidence` for a model decision); graph traversal weighs `model` at 0.6 times its confidence; search's graph boost weighs a model edge the same way and lists the provenances of the connections that lifted a passage, a path counting as its weakest edge (`parts.graphVia`). Proposals are never edges.
- **Setup report.** `model: { available, on, read, edges, waiting }`; the card shows the estimate, the run's progress, and the counts.

## Communities, hubs and topic summaries (wave 2)

- **Detection** (`app/graph/communities.js`, pure): Louvain modularity in plain JS, with each level's communities split into their connected pieces (the guarantee Leiden adds). Edges weigh their kind times their provenance (the weights `query.js` walks with) times confidence; superseded edges are left out. Tag and folder nodes never shape communities: their `tagged` and `in_folder` edges only label them (tags at least 40% of members carry, a folder half of them sit in). Nodes are visited in id order and ties go to the lower index, so one graph always gives the same communities, whatever order the rows come in. A community keeps its id while at least half its members stay together (Jaccard), so a summary keeps its community when the hub changes; a new community's id is `c:` and a hash of its hub, which names no note.
- **When it runs** (`app/graph/topics.js`): in a worker thread (`communityWorker.js`, unpacked from app.asar with `communities.js`; `scripts/check-package.mjs` fails a package without them) on its own read-only connection, after the first build and 10 seconds after updates settle; main writes the answer in one transaction. If a worker cannot start, the same code runs in the main process for that cycle on a vault of up to 5,000 nodes; a larger one skips the cycle. On a generated graph of 4,000 nodes and 12,000 edges: about 85 ms in the worker (read 13 ms, detection 50 ms) and 30 ms to name and write.
- **Names**: with no model, the strongest member of the first kind in project, topic, company, person, note, meeting, decision; a note or person hub gets the shared tag or folder in front (`design: Weekly review`). With Settings, Memory, Topics, "Name topics and draft summaries with your model" on (off by default; the card shows the calls and cost at API rates before it is turned on), the person's model source names up to 20 communities in one call. A model name stays while the community's strongest members hold, and lands only on a community whose members are still the ones it was asked for. Each community is asked once per set of strongest members and each draft once per set of sources, whatever the answer, and topics make at most 30 model calls a day. The switch turns on only once the graph is built and a model source is set, so the cost was shown first.
- **Read guard**: the read filter the model pass uses too (`main.js` noteMayRead, `memoryModelPass.js` createMayRead). A confidential note (frontmatter, tag or folder mark, or confidential text), one the read guard keeps out (opted-out, private or secret paths), one with a line the opt-out list withholds, or one that names an address on the never-listen list never names a community, never goes to the model, and is never a source of a summary, whatever Let the agent read confidential notes says: a topic summary is a plain note.
- **Hubs**: distinct neighbors and edge count over current edges, tag and folder edges left out; overall or in one community.
- **Tools**: `communities` (biggest first with name, size, hub and top members; with `id`, a community id, its name or any node in it, that community's members) and `hubs` (overall or `community`), budgeted like the others. `explain` and `entity` show a node's community. A community or hub that names an opted-out customer is withheld; a node whose community does keeps its answer with the community blanked.
- **Topic summaries** (`rules/topicSummaries.js`, rule `note.topic-summary`): for the biggest communities with at least 5 notes, up to 5 new items at a time, a summary that cites each source note: the model's draft when it is on and was written from the sources as they read now, else the main notes, people, decisions and each note's first sentence. Approve runs the `summary` op, which writes only under the Quorum folder (`<Quorum folder>/Topics/<name>.md`) and only over a note marked `quorum: generated`. Only generated notes in that folder are matched and refreshed, and the refresh op carries the configured folder; a summary whose community took a new id is found by its sources (half or more) and written again with the new id. The note records `community`, `summary_of` and `source_hashes`; when at least 30% of its sources changed, joined or left (and at least 2), a refresh item offers it written again. `note.summary-stale` leaves these notes to this rule.

## Cloud graph sync (wave 2, as built)

`app/ee/graphSync.js` with migration `0049_graph_links.sql`. Cloud only; the Local edition has no such module and nothing leaves the Mac.

- **Publish.** After every sync pull, each Mac lists its own notes the server holds in a knowledge base. A note publishes when its text on disk is the text sync pushed and the graph has read it; its edges (`edgesFromSource`, `person` edges included) go to `links` through `graph_put`, which replaces the note's set in one transaction, and only when the set's hash changed. A note that is now excluded (private folder, confidential, opted-out customer) withdraws its set. An edge end that is another note goes only when that note is in the same knowledge base; an entity goes by id and name. Only `explicit`, `rule` and `person` edges go: a `model` edge never does, at any confidence, and the server refuses one; a reading a person approves in Review becomes a `person` edge. A fact superseded by one from a note that does not publish stays on the Mac; a note whose superseding fact waits for its push waits too; a local fact that a teammate's newer fact replaced on this Mac still goes as current. Names are cut to 300 characters; an edge over the server's size caps stays on the Mac and the rest of the note goes.
- **Read.** `graph_heads` lists, per readable knowledge base note, the hash of its edge set; the Mac reads `links` only for notes whose hash changed. Teammates' edges keep provenance, source line, confidence and validity, sit under the source path `team:<path>`, and carry `props.team` (knowledge base, note, author, edge key). Entities share ids with the local graph; a teammate's notes, meetings and decisions get `<kind>:team:<path>` ids. A node id must start with its kind (the server checks it, and the reader refuses a row that does not), and a teammate's edge never attaches to a local node of another kind. Supersession is sent as edge keys and resolved after every read.
- **Access.** `links` reads stay as 0043 set them (your rows, or rows on a note you can read). 0049 narrows writes: a row is written only as yourself on a live note you own, a graph row only on a knowledge base note, and update and delete only by the row's owner. `graph_put` runs as the caller. A note that leaves its knowledge base (made private, moved to another knowledge base, deleted) loses its graph rows, and so do the notes whose edges name it (a trigger); their authors' Macs publish them again. Rows handed to an heir (account hand-over) are deleted, since the heir's Mac has no copy to publish from. `graph_heads` is a definer function that checks each note once with `note_readable` before joining its rows. Signing out, turning sync off or switching workspace removes the team's edges and stops a run under way before its next write or put; a clear while no graph is open waits for the graph.
- **Offline.** Nothing counts as sent or read before the server answered; the next run sends or reads the difference again. Runs are coalesced (one at most every 15 seconds).

## Context rot

Quorum guards against two kinds: a memory that grows stale and contradictory, and AI tools drowning in too much context.

Already in place: stale, duplicate, near-duplicate, oversized and contradiction rules; the learned facts list has a character budget.

Added in this build:

1. **Supersession, not deletion** (graph-core). Changed facts end their validity and point at what replaced them; queries return current facts by default and history on request.
2. **Budgets everywhere** (mcp). Every retrieval tool trims to a token budget, puts the strongest items first and last, and states what it left out, so an agent asks a narrower question instead of reading more.
3. **Recency and confirmation in ranking** (search). Superseded and long-unconfirmed facts rank lower; facts confirmed by recent meetings rank higher.
4. **Consolidation reviews** (setup). Duplicates merge into one canonical note on Approve; oversized notes are offered a split; summaries record the hashes of their sources and are marked stale when a source changes.
5. **Instruction file hygiene** (setup). The scan measures CLAUDE.md, AGENTS.md and similar files (a note named `instructions` only at the vault root or in `.github/`) against a size budget and lists one over it with its largest sections, for the person to shorten. A line that states a decision a newer decision replaced (the file is the losing side of a `supersedes` edge, and the line still holds that decision's text) is a Review item that marks it out of date. Their links to missing notes are broken link items.
6. **Freshness in the setup report** (setup). Share of dated facts confirmed in the last 90 days (a fact from an undated note counts in neither the share nor the total; with no dated facts, the share of notes updated or verified), open contradictions, stale summaries.

## Embedding model choice

Local bge-small-en-v1.5 is the default: free, private, offline, already shipped. A full index of a 3 million token vault costs nothing and takes minutes on Apple Silicon. Hosted models (Voyage 4 lite at $0.02 per million tokens, Voyage 4 at $0.06, with 200 million free tokens per account) would cost cents per vault, but would send every note to a third party, which the Local edition promises not to do. The eval compares bge-small with a stronger local model (for example EmbeddingGemma 300M) and, on a non-confidential test vault only, a hosted model, before any change.

### Real-vault eval (2026-11-20)

The eval ran on a real personal vault: 2,195 notes, about 4.8 million tokens, 28,350 chunks, 3,735 graph nodes and 12,538 edges. The 65 questions are the kind the owner and their agents ask, written by hand with the expected notes, and they stay in that vault. No question names or expects a personal or confidential note. |---|---|---|---|---|---|---|

| paraphrase | 13 | 0.846 / 0.788 | 0.808 / 0.650 | 0 / 0 | 0.923 / 0.769 | 0.846 / 0.660 |
| person | 10 | 1.000 / 1.000 | 1.000 / 0.920 | 0.250 / 0.250 | 1.000 / 1.000 | 1.000 / 0.950 |

Each cell is recall@10 / MRR. Hybrid without vectors is `--weights '{"vec":0}'`.

- **Vectors earn their place in ranking.** Against hybrid without vectors they add 1.5 points of recall@10 (one paraphrase question found) and 8.5 points of MRR, with gains on every type and the largest on recent (+20 points MRR) and paraphrase (+11). Keyword alone already finds 95% of the expected notes on real notes, so most of the vector gain shows up as the right note ranking first.
- **Cost.** Embedding all 28,350 chunks took 1,187 s at 2 threads (24 chunks a second), once per vault; later edits embed only changed chunks (one note's update took 32 ms). Vectors are 43.5 MB of the 172.5 MB search and graph database (about 20 MB per 1,000 notes). Hybrid search takes a median of 32 ms and 45 ms at p95, the query's embedding included.
- **Weights stay as shipped.** Variants (vec 0.5 and 1.5, graph 1, graphNamed 0, kindHint 1, recency 0) all scored 0.969 recall@10, the same as the shipped weights. Recency 0 raised MRR to 0.887 (+2.2 points); that is two or three questions out of 65 and below the bar for a change. Without vectors, hybrid ranks below keyword alone on MRR (0.780 against 0.858), so the recency, kind and named-node boosts rely on the vector list to keep the best note first.
- **Graph alone does not work as search.** It answers only questions that name a node it knows (0.146 recall@10 overall). Its job is the graph tools and the named-node boost, as the audit planned.

**Vector duplicates and orphan links: measured, not built.** Note-level vectors (the mean of a note's chunk vectors) were compared for every pair of notes that may merge (dated notes, meetings, decisions and notes under 200 characters left out; confidential pairs left out). Of 830 pairs at cosine 0.92 or more, 129 were already near-duplicates by shingles. A hand check of 20 of the rest found 1 true duplicate (5% precision): the others were parts of one series, a brief and its article, two reviews of one pull request, or two reports on one topic, which must not merge. At cosine 0.97 or more, 2 of the 18 new pairs were true duplicates (11%). bge-small puts notes on one topic too close together to tell a copy from a neighbor, so duplicates stay with exact text, shingles and aliases. Related-note suggestions for orphans have nothing to work on here: the orphan rule finds 2 notes on this vault, and both are exact copies of notes in another folder, which the duplicate rule already covers. "Vector duplicates wait for search" is closed: they do not ship.
